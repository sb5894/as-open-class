# 공개보고회 사이트 디자인 방향 및 인수인계

작성일: 2026-10-21. 이 문서는 사용자와 검토한 디자인 피드백과 현재 기준 시안을 다음 작업자에게 전달한다. 과거 실험안보다 **아래 기준과 최신 사용자 지시**를 우선한다.

## 1. 가장 먼저 확인할 파일과 현재 작업 범위

**2026-10-21 후속 구현:** 사용자가 메인 화면 반영·임시 채널 배포를 요청했다. 새 상단 문구와 웹 전체 400·600·700 세 굵기 규칙은 [결정 기록](결정%20기록.md) 상단을 우선한다. 아래 시안 원문의 제목·소개 문장·여섯 굵기 설명은 시안 작성 당시 기록이며, 후속 코드의 문구·글꼴 설정으로 되돌리지 않는다. 기존 초록/살구색과 본문 보존 방향은 이어진다. 실제 배포·검증 상태는 [진행 현황](진행%20현황.md)을 따른다.

**이 HTML은 당시의 독립 기준 시안이다.** 2026-10-21 후속 요청으로 실제 앱에 새 문구·공통 헤더·Noto 세 굵기·지도/신청 수정·회귀 보정을 반영하고 정식 Hosting에 배포했다. 최신 앱을 이 파일로 재생성하지 않는다. 아래 검토 과정과 측정 전 설명은 시안 작성 당시 기록이며, 현재 코드·검증·배포 상태는 진행 현황 상단을 우선한다.

HTML은 프로젝트 안에서 파일로 직접 열 수 있다. 학교 로고·안내도 배경·교육 모델 그림은 `../../public/assets/`의 기존 자료를 참조한다. 파일만 다른 곳으로 옮기면 이미지 경로가 끊어진다. GitHub 파일 화면은 HTML 소스를 보여주며 웹사이트를 호스팅하지 않는다.

파일 직접 열기에서는 신청/안내 링크가 기존 정식 사이트로 이동하고, Vite의 localhost/127.0.0.1에서 열면 같은 서버의 `/register`, `/guide`로 이동한다. 이 HTML 자체에는 신청 저장 기능이 없다.

## 2. 이용자와 디자인 우선순위

이 사이트는 안성초등학교 공개보고회 참석자의 안내 확인과 참관 신청을 위한 모바일 웹이다. 이용자는 구글 폼 같은 단순한 입력 플랫폼에는 익숙해도, 새로운 웹 구성에는 익숙하지 않을 수 있다. 연령대가 높은 참관자가 포함될 수 있다는 사용자 피드백이 있었다.

우선순위는 다음과 같다.

1. 무엇을 누르면 되는지 명확하게 알 수 있는 화면.
2. 일시·장소·신청 기한·등록 위치를 찾기 쉬운 구조.
3. 지정 문구와 실제 수업·공간 정보의 정확성.
4. 모바일 가독성, 충분한 터치 영역, 일관된 탐색.
5. 위 조건을 만족하는 범위의 시각적 완성도.

처음에는 사용자가 `gpt-tasteskill`을 최우선 방향으로 요청했다. 이후 실제 이용자에게 직관성이 떨어진다는 피드백으로 방향을 조정했다. **현재 사용자 선택이 스킬의 극적 레이아웃·애니메이션 규칙보다 우선한다.** 스킬의 간격·대비·제목 위계는 참고할 수 있지만, GSAP·캐러셀·마키·가로 탐색·스크롤 고정을 다시 넣지 않는다.

## 3. 검토 과정에서 확인한 문제와 최종 선택

| 피드백 | 후속 작업에서 지킬 방향 |
|---|---|
| 첫 시안의 남보라색과 장식적 구성은 공식 행사 느낌은 있지만 낯설고 무겁게 느껴질 수 있었음 | 기존 초록 계열로 통일. 현재 색상 기준을 유지 |
| 구글 폼에 익숙한 이용자에게 여러 형태의 카드·감성 소제목·움직임이 탐색 부담이 될 수 있음 | 명확한 링크와 익숙한 본문 구성. 핵심 정보가 동작 없이 읽혀야 함 |
| 단순화 과정에서 초대 문구를 축약·변경했으나, 사용자에게 지시받은 문구였음 | 지정 초대 문장·연구 주제·공문 안내는 임의 변경 금지 |
| 사용자는 첫 시안의 상단은 살리고 아래는 기존 사이트를 유지하는 결합안을 요청함 | 상단만 현재 시안 적용, 아래 네 영역은 기존 순서·카드·표 구성 유지 |
| 강조색을 노랑·핑크·하늘색으로 바꿔봤지만 선호되지 않았음 | 상단 신청 버튼은 최초 살구색으로 복귀. 제목은 흰색 |
| 화면 아래 고정 신청 버튼은 계속 진초록이어야 한다고 명시함 | 강조색 실험과 관계없이 하단 고정 버튼은 진초록 + 흰 글자 |
| 상단/본문 글꼴이 달랐음 | 모든 영역을 Noto Sans KR로 통일. 제목 위계는 크기·굵기·간격으로 표현 |

색을 다시 제안하거나 이미 거절된 실험을 반복하지 않는다. 변경 필요성이 생기면 이유와 영향을 설명하고 사용자 요청 범위에서 작업한다. 위 피드백은 화면 관찰과 사용자 선호에 따른 것이며 전환율 개선을 실험으로 입증한 결과는 아니다.

## 4. 현재 기준 시안의 구성

### 상단

- 학교 로고·학교명·행사명 보조 문구.
- 오른쪽 위에 기존과 같은 밑줄형 **신청하기 / 둘러보기** 링크. 두 링크는 최소 높이 44px.
- 짙은 초록 배경의 초대 영역. 기존 학교 안내 일러스트를 낮은 대비의 배경으로 사용.
- 큰 제목은 흰색의 `서로의 다름이,` / `함께의 배움으로.` 두 줄.
- 아래 두 문장은 모든 화면에서 구분된 줄로 표시:

  > 언어와 문화의 다양성을 배움으로 잇는 교실.
  > 안성초의 연구와 실천을 나누는 자리에 초대합니다.

- `참관 신청하기`: 살구색 채움 버튼, `/register`로 이동.
- `학교·수업 안내`: 초록 배경 위 흰 글자·외곽선 버튼, `/guide`로 이동.
- 신청 전에도 수업 안내와 지도안을 볼 수 있다는 안내.
- 행사 일시·장소·주소·신청 마감 요약.

좁은 화면에서 문장이 추가로 줄바꿈되는 것은 허용하되, 위 두 문장을 한 줄 흐름으로 합치지 않는다.

### 상단 아래 본문

현재 운영 소스에서 가져온 아래 네 영역을 그대로 유지한다.

1. **행사 소개:** 연구 주제, 초대 문장, 행사 정보 목록, 출장 협조 공문 안내.
2. **공개보고회 일정:** 기존 4열 표와 시간·내용·장소, 2부의 묶음 구조.
3. **만남·배움·어울림이란?:** 기존 모델2 표·제공된 원본 그림·설명.
4. **공개수업 학년별 중점:** 기존 표.

현재 시안은 이 본문의 DOM과 문구를 보존했으며, 최종 글꼴 통일 지시에 따라 글꼴만 변경했다. 본문을 새 타임라인이나 카드 이야기 구조로 바꾸는 것은 현재 방향이 아니다. 일정표 글씨가 좁은 화면에서 작은 문제는 남아 있지만, 이를 이유로 구조와 문구를 임의 변경하지 않는다. 필요하면 별도 개선 작업으로 제안한다.

### 모바일 하단 고정 영역

- 신청 마감 안내 + 진초록 `참관 신청하기` 버튼.
- 현재 600px 이하에서 표시하며 데스크톱에서는 숨긴다.
- 마지막 표와 링크가 고정 바에 가리지 않도록 하단 여백을 유지한다.
- 이 고정 바를 신청 폼에 그대로 확대 적용하지 않는다. 실제 적용 시 키보드·제출 버튼 가림을 별도 확인한다.

## 6. 문구 보존 규칙

현재 시안의 새 상단 문구는 사용자에게 보여주고 방향으로 선택된 상태다. 그 아래 원래 초대장 문구는 반드시 보존한다. 디자인을 바꾸면서 전체 문장을 요약하거나, 정식 행사명에서 `다문화교육`을 빼거나, 날짜·시간을 임의 표기 방식으로 바꾸지 않는다.

특히 다음 원문을 유지한다.

> 안성초등학교는 「상호문화적 (만남·배움·어울림) 이중언어 교육 프로그램 운영을 통한 미래 핵심역량 함양」을 주제로 정책연구학교를 운영하고 있습니다.

> ※ 참석 신청을 해주신 분의 소속 기관으로 출장 협조 공문을 보내 드릴 예정입니다.

- 일시: `2026. 11. 11.(수) 12:50~16:00`
- 장소: `안성초등학교 (등록: 본관 1층 중앙현관)`

## 7. Noto Sans KR와 폰트 최적화

### 현재 상태

- 사용자가 전체 글꼴을 Noto Sans로 통일하도록 명시했다. 한국어용 **Noto Sans KR**로 상단·본문·표·메뉴·버튼을 통일했다.
- Google Fonts CSS에서 `400;500;600;700;800;900` 여섯 굵기를 요청한다. Outfit 요청은 제거했다.
- `display=swap`을 사용한다. 폰트가 도착하기 전에는 대체 글꼴로 글자를 표시한다.
- 로딩 실패 시 `sans-serif`로 표시된다.
- **실제 폰트 전송량, 로딩 시간, 실제 적용 성공과 느린 네트워크 성능은 아직 측정하지 않았다.** 기존 검증은 CSS 지정 확인이다. 계산된 `font-family`가 Noto라고 해서 실제 Noto 파일이 렌더링에 쓰였다는 뜻은 아니다.

### 최적화 방향

전체 페이지에 적용하는 것 자체보다 실제로 다운로드하는 문자 범위·스타일·굵기·파일 수가 비용에 영향을 준다. 같은 글꼴을 여러 요소에 지정했다고 요소마다 파일을 새로 받는 것은 아니다. 여섯 굵기를 요청했다고 항상 완전한 한글 글꼴 여섯 벌을 내려받는다고 단정해서도 안 된다. 제공 CSS와 브라우저의 실제 요청을 확인한다.

1. **현재 상태부터 측정:** 모바일 크기, 캐시 없는 첫 방문과 재방문을 나눠 폰트 요청 수·실제 전송 바이트·완료 시간·첫 화면 글자 표시·LCP/CLS를 기록한다. 느린 모바일 네트워크 조건도 포함한다. 요청 실패와 대체 글꼴 표시를 구분한다.
2. **굵기 정리:** 현재 CSS의 400/500/600/650/700/800 등 실제 사용을 조사한다. 본문·강조·제목의 3~4단계로 정리할 수 있는지 검토한다. 900 등 사용하지 않는 굵기 요청은 후보로 삼되, 변수 글꼴 공유 여부 때문에 절감량을 미리 단정하지 않는다.
3. **전달 방식 비교:** Google Fonts의 분할 제공과 WOFF2 변수 글꼴/부분 글꼴 자체 호스팅을 실제 바이트 기준으로 비교한다. 자체 호스팅이 자동으로 더 가벼운 것은 아니다. 전체 CJK 파일을 무작정 추가하지 않는다.
4. **부분 글꼴 범위 검토:** 초대장에 있는 문자만 추출하면 신청·안내·지도안 관련 UI와 수업별 문구, 사용자 입력에서 빠지는 문자가 생길 수 있다. 데이터 전체와 기호·숫자·영문까지 검토하고 대체 글꼴 경로를 보존한다.
5. **렌더링 안정성:** `swap`을 기본으로 유지하고 대체 글꼴과 행간·크기를 조절해 글꼴 교체 시 줄바꿈 변화와 레이아웃 이동을 줄인다. 모든 조각을 preload하지 말고 첫 화면에 필요한 자원인지 확인한다.
6. **최종 판단:** 가독성·한글 일관성·첫 화면 속도를 함께 비교한다. 사용자 요청 없이 시스템 글꼴로 되돌리지 않는다. 작은 KB 수치만으로 글자 굵기나 대비를 희생하지 않는다.

실제 적용 확인은 Network의 `.woff2` 응답·전송량과 개발자 도구의 실제 렌더링 글꼴을 확인한다. 필요하면 `document.fonts.load()` 결과와 글꼴 상태를 함께 확인한다. CSS 속성 문자열만 확인하는 자동 검사를 로딩 성공 증거로 삼지 않는다.

참고: [웹폰트 권장사항](https://web.dev/articles/font-best-practices), [웹폰트 최적화](https://web.dev/learn/performance/optimize-web-fonts), [Google의 한국어 글꼴 분할 제공 설명](https://developers.googleblog.com/en/google-fonts-launches-korean-support/). 이 자료를 근거로 한 권고이며 이 프로젝트의 측정 결과는 아니다.

## 8. 실제 코드 반영 시 주의할 구조

기준 HTML은 독립 시안이라 첫 실험의 미사용 CSS와 여러 단계의 색상 override가 남아 있다. 그대로 `src/styles.css` 전체에 붙여 넣지 않는다. 실제 사용 요소를 추려 의미 있는 CSS 변수/클래스로 정리하고 기존 TypeScript/Vite 구조에 반영한다. 새 프레임워크·GSAP는 필요하지 않다.

- `src/main.ts`의 메인 상단에 시안의 히어로·요약을 적용하되, 본문 컴포넌트는 재사용한다.
- 기존 내비게이션과 메인 시안의 메뉴를 중복 생성하지 않는다.
- 시안의 `../../public/assets/...`를 운영 코드에 복사하지 않는다. 기존 `/assets/...` 자산 경로를 사용한다.
- 시안의 localhost 감지 스크립트를 SPA 라우터 대신 사용하지 않는다. 기존 링크 처리와 focus/뒤로 가기를 유지한다.
- `.legacy-content * { all: revert; }`는 시안에서 두 디자인의 CSS를 격리하기 위한 임시 장치다. 운영 코드에 그대로 이식하지 않는다.
- 기존 지도·층별 안내·PDF·신청 오류 스타일에 새 전역 CSS가 영향을 주지 않도록 범위를 제한한다.
- 예전 시안 생성 스크립트나 오래된 캡처로 현재 파일을 재생성하지 않는다. 보존한 HTML과 이 문서를 기준으로 한다.

## 9. 다음 작업자가 진행할 순서

1. 이 문서와 기준 HTML을 읽고 현재 방향을 확인한다. 처음부터 새 디자인 제안을 시작하지 않는다.
2. 사용자가 요청한 실제 반영 범위를 확인한다. 이번 문서 정리는 운영 변경 지시가 아니다.
3. 운영 메인에 옮길 때 기존 본문 컴포넌트·지정 문구를 보존한다.
4. 폰트 최적화는 먼저 측정하고, 필요한 굵기와 전달 방식만 조정한다.
5. 아래 검증을 수행하고 실제 수행 결과와 남은 항목을 진행 현황에 남긴다.
6. GitHub 푸시와 Firebase 배포는 별도 작업으로 보고한다. 배포는 해당 작업의 사용자 지시 범위를 따른다.

### 검증 기준

- Chromium·WebKit에서 320/390/430px와 넓은 화면: 가로 넘침, 글자/표/메뉴 줄바꿈, 큰 제목, 두 문장 구분.
- 메뉴와 상단/고정 신청 버튼의 목적지·44px 이상 터치 영역·본문 바로가기.
- 하단 고정 바의 마지막 콘텐츠/포커스 가림 없음. 모바일 주소창과 safe-area, 실제 iPhone/Android 확인.
- 실제 앱 반영 시 신청 키보드, 필수 오류, 수업 선택 0~2개, 실패 후 입력 보존, 저장 성공 후 완료 표시.
- 모델 링크 이동, 교실/층 복귀, PDF 지연 로딩과 미제공 표시 보존.
- 큰 글자 설정, 키보드 탐색, 화면 읽기 프로그램, 느린 네트워크, 폰트 로딩 실패 시 읽기 가능 여부.
- `npm.cmd run check`, `npm.cmd run build`. 실제 코드 변경 범위에 맞는 기존 테스트도 실행한다.

### 검증 상태의 한계

현재까지의 시안 검증은 두 엔진·네 화면 크기의 넘침/이미지/메뉴/줄바꿈/글꼴 지정 및 원래 본문 마크업 보존이다. 캡처를 직접 확인했고 타입 검사·빌드는 통과했다. 실제 휴대폰, 스크린리더, 글자 확대, 실제 폰트 전송량 및 성능 개선은 미검증이다. 실제 신청 행을 새로 저장하지 않았고 운영 화면도 바꾸지 않았다.

## 10. 정리한 자료의 범위

이번 디자인 실험에서 만든 미채택 HTML·검토 HTML·중간 캡처·오래된 검증 JSON·사용하지 않는 GSAP 자산은 정리했다. 현재 기준 HTML·현재 캡처·현재 검증 기록만 보존한다. 과거 학교 지도/시설/콘텐츠 검토 증거와 개발 문서·요구사항·원본 자료는 별도 업무 기록이므로 보존한다.

후속 작업 시 이 문서를 현재 결과에 맞게 갱신하고, 진행 현황에 변경·검증·미완료 항목을 기록한다. 파일 이름의 `taste`는 첫 스킬 검토에서 유래한 것으로, 그 스킬의 과거 실험 방향을 되살리라는 뜻이 아니다.
